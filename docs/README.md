# Azure OpenAI Chatbot — Serverless Multimodal Assistant

A full-stack conversational assistant built entirely on Microsoft Azure. It answers questions through an LLM, remembers the conversation, and can describe images pasted straight into the chat.

Built from scratch as a hands-on study of Azure's serverless and AI stack — going from an empty subscription to a deployed, multimodal chatbot with CI/CD.

**Live demo:** https://victorious-water-0f735041e.7.azurestaticapps.net/

## What it does

- **Ask anything** — send a question and get an answer generated by an Azure OpenAI model.
- **Remembers context** — ask "What is the capital of Brazil?" then "and what is its currency?" and it knows you still mean Brazil.
- **Understands images** — paste a screenshot (`Ctrl+V`), drag-and-drop, or attach a file, and the assistant describes it. Follow-up questions about the same image work too.

---

## Architecture

```
Browser (Static Web App)
        |
        |  POST /api/ask  { session_id, pergunta, imagem? }
        v
Azure Function  (Python, HTTP trigger)
        |
        |-- text ---------------------> Azure OpenAI (gpt-5-mini)
        |-- image (base64) --> Blob Storage --> signed URL --> Azure OpenAI
        |-- history <-----------------> Table Storage (per session_id)
        v
JSON response  { pergunta, resposta, session_id }
```

Every piece lives in a single resource group. The function is the only compute; everything else is managed storage or a managed model.

## How it works

### Conversation memory
Each browser tab generates a `session_id`. The function stores every message in Table Storage, partitioned by that id, and reloads the full history on each request so the model always sees the ongoing conversation. Without a `session_id`, the endpoint stays stateless.

### Image understanding
The frontend resizes the pasted image (max 1568px) and sends it as base64. The function decodes it, uploads it to Blob Storage under a unique name, generates a read-only **SAS URL** valid for a limited time, and passes that URL to the model. Only the URL — never the raw image — is stored in the conversation history, so follow-up questions can re-load the image on demand. This sidesteps Table Storage's 64 KB-per-property limit.

### Security notes
- The function uses **anonymous auth** so no key is exposed in the frontend JavaScript.
- **CORS** is restricted to the Static Web App's domain, blocking browser calls from other origins.
- Secrets (`local.settings.json`) are git-ignored and stored as Application Settings in Azure.
- Known limitation: CORS does not stop direct `curl` calls. A production version would front the API with a server-side proxy or Azure API Management holding the credentials.

## Running locally

**Prerequisites:** Python 3.11, Azure CLI, Azure Functions Core Tools.

```bash
# backend
cd backend
py -3.11 -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

Create `backend/local.settings.json` with your own values:

```json
{
  "IsEncrypted": false,
  "Values": {
    "AzureWebJobsStorage": "",
    "FUNCTIONS_WORKER_RUNTIME": "python",
    "AZURE_OPENAI_ENDPOINT": "https://<your-resource>.openai.azure.com/",
    "AZURE_OPENAI_KEY": "<your-key>",
    "AZURE_OPENAI_DEPLOYMENT": "gpt-5-mini",
    "STORAGE_CONNECTION": "<your-storage-connection-string>"
  }
}
```

```bash
# run the function
func start
```

Then open `frontend/index.html` (adjust `API_URL` to your endpoint) or serve it locally.

### Example request

```bash
curl -X POST "http://localhost:7071/api/ask" \
  -H "Content-Type: application/json" \
  -d "{\"session_id\": \"demo\", \"pergunta\": \"What is the capital of Brazil?\"}"
```

## What I learned

This project was as much about the Azure platform as about code. Highlights:

- Provisioning and wiring Azure resources (Functions, OpenAI, Table & Blob Storage) via CLI and portal.
- The difference between **Table Storage** (structured, key-value) and **Blob Storage** (files) — and why each fits a different job.
- **SAS tokens** for granting temporary, scoped access to private storage.
- Why **secrets can't live in a frontend**, and how CORS + anonymous auth mitigate it.
- Setting up **CI/CD** with GitHub Actions so a push redeploys the site automatically.
- Reading errors carefully — e.g. an image "download failed" error actually proved the model *was* multimodal.

## Possible next steps

- Generate SAS URLs at read-time instead of storing them (they currently expire).
- Add a Blob lifecycle policy to auto-expire old images.
- Trim or summarize long histories to control token usage.
- Front the API with Azure API Management for real access control.
